# `streaming` — handover: the media plane behind its ports (PS0), then the run, entitlement and playback

`streaming.md` §3 puts the media plane behind four ports and `adr-stream-entitlement.md` decides how
a right to watch reaches the edge. PS0 built the service and the ports with a fake provider (§0,
§0a); each later PRD replaces its own section below, with its own proofs and gaps. No user sees
anything until the run desk (PS1) and playback (PS3).

## 0. Three processes, one database

| Process | Entry | Serves |
| --- | --- | --- |
| API | `node dist/main.js`, `PORT` (3005 in `.env.example`) | `/health/liveness`, `/health/readiness`; in development `/docs`, `streamingServiceApi`'s Swagger UI |
| consumer | `node dist/consumer.js` | `arthome.ticketing.date_sales`, `arthome.ticketing.account`, `arthome.catalog.date` (the entitlement projection, §0c; `catalog.date.drafted.v1` prepares a run, §0b), group `streaming`; retrying on `arthome.streaming.retry`, dead-lettering to `arthome.streaming.dlq` |
| sweeper | `node dist/sweeper.js` | the run's presence pass and its end by itself (§0b); the replay asset's five passes and its provider calls (§0f) |

**Stop every process before `migration:run`.** A migration may drop a column the running build still
reads.

Generated by `tools/schematics`'s `service` (`--name streaming --port 3005 --topics run:12
--consumer --sweeper`) and kept as written. Every process reads `DATABASE_URL` through
`libs/config` (`NODE_ENV` required, never defaulted), closes its pool on SIGTERM, and is booted as
its entry point boots it by `src/boot.itest.ts`. Migrations: the generated one (`outbox_event`,
`processed_message`, `idempotency_record`), then PS2's entitlement projection (§0c) PS1's run desk (`run`, `stream_key`, `incident`, §0b) and PS5's `replay_asset` (§0f). The database `streaming` is created by
`infra/postgres/init-databases.sql` on an empty data directory only: on a stack already up, create it
by hand. The connector is `infra/debezium/streaming-outbox.json`, registered by hand with AGENTS.md's
loop; `arthome.streaming.run` (12 partitions, read by catalog) is this service's, and carries the
run desk's six event types on the date's key (`STREAMING_EVENT_TOPICS`, `src/streaming-events.ts`).

**The API is born on its internal contract** (D-121): every route it will serve is an operation of
`@arthome/contracts/streaming-service-api`, bound with `@Endpoint`: PS1 binds the run desk's eight,
PS3 and PS4 bind theirs. `edgeProviders` (`src/edge-providers.ts`) binds core's `service` identity, whose principal is
`{ callingService, userId, profileId?, deviceId? }` from the token's `iss`, `sub`, `pro` and `did`
(a claim the token lacks is absent, never null), and the `callerService` rule, which refuses
403 `api.forbidden` a BFF a route does not name. A route that reads the profile refuses a token
without `pro` the same way (C3 S3). `main.ts` calls `serveEndpoints` then `mountStreamingDocs`, as
the boot suite does.

**The API does not boot in production** while the fake is the only provider: `AppModule` imports
`MediaModule`, which refuses to bind it there (§0a). The sweeper imports it too since PS5 (§0f); the
consumer imports it when a later PRD needs it. A real provider's binding will read `PLAYBACK_SIGNING_KEY`, and PS1's stream
keys `STREAM_KEY_SECRET`, both required in production (§0a), beside `JWKS_URL`.

## 0a. Media ports and the fake (PS0)

`src/media/media-ports.ts` holds the four ports, provider-neutral types only: the stream path is the
domain's (random, PS1), the recording reference the provider's (`RecordingRef`, opaque), and no
provider identifier crosses into the domain. The ports live here rather than in core while
`streaming` alone implements and calls them; they move to core the day a second implementation or
a contract needs them. `src/media/media-tokens.ts` holds their tokens. Only `media.module.ts` and
the suites import the fake; domain code imports the ports and the tokens.

- **`LiveIngestProvider`**: `ingestCapabilities` (`protocols` among rtmps, srt, whip;
  `monitorPaths` among whep, ll_hls, WHEP never promised (D-019); `carriedCodecs` per protocol),
  `ingestUrlFor`, `monitorUrlFor` (null when not offered), `disconnect`, and `attachIngestHooks`,
  called once at boot: until then every feed is refused. `codecsCarried(capabilities, sample)` is
  `TechnicalCheckProbe.codecCarried` for C2's `technicalCheckFailuresOf`, core naming no codec.
- **The ingest hooks**, the provider's calls into the domain: `IngestAuthorizer.authorize({
  streamPath, presentedKey, protocol })` answers accept, or refuse with a reason, before anything
  is accepted; `IngestLifecycleListener` (`publisherOnline`, `publisherOffline`, `workerFailed`)
  reports with each instant and decides nothing (`adr-stream-entitlement.md` §6). PS1 implements
  both and attaches them; a real media server's ingest route is the real adapter's slice.
- **`PlaybackProvider`**: `playbackCapabilities` (`supportsSignedCookies`,
  `supportsQueryTokenRenewal`, `protocols`, `drmSystems`, `geoRestriction`) and `sign(grant)`: the
  grant names the date, the session scope, the token's claims (`sub` the profile, `did`, `dat`,
  `sid`, `qmax`, `scope`, `jti`), `expiresAt` and the mechanism; the answer is the manifest URL,
  the query token or the cookies to set, and the `kid`. A mechanism the capabilities do not declare
  throws `PlaybackSigningUnavailable`: a port that cannot sign refuses to serve.
- **`RecordingProvider`**: `recordingCapabilities` (`recording`, `masterAtIngest`), `start`
  answering a `RecordingRef`, `stop`, `status` (`ready`, `durationSec`, `RecordingNotFound` for a
  reference it does not hold), `delete`, harmless twice.
- **`StreamingMetricsProvider`**: `sample(streamPath)`, a `FeedSample` (`measuredAt`, `protocol`,
  `videoCodec`, `audioCodec`, `ingestUpKbps`, and `jitterMs`, `lostPackets` on WHIP only) or null
  with no publisher.

Each port names its capabilities after itself: one provider may implement all four, and ingest and
playback both declare `protocols`, from two vocabularies (ours, and the contract's
`PlaybackProtocol`). The playback types read `@arthome/contracts/streaming`'s `PlaybackProtocol`,
`DrmSystem`, `EdgeRenewalMode` and `QualityCap`, and core's `WatchScope`.

**`FakeStreamingProvider`** (`src/media/fake-streaming-provider.ts`) implements the four on one
instance, on the injected `CLOCK`: its instants are computed from the clock, never waited for.

- `publish(streamPath, key, { protocol })` refuses a protocol it does not ingest, then any feed
  while no hooks are attached, then asks the authorizer and accepts nothing it refuses; a second
  publisher on a path that has one is refused, as a real media server does.
- `drop` (a cut at the venue), `resume` (the same encoder back, authorised again with the key it
  presented, so a key rotated during the cut lets nothing back) and `disconnect` raise the
  callbacks with their instants. A resume before `FAKE_WORKER_GRACE_MS` (3 s, the fake's own
  parameter, read by no domain code) keeps `manifestGeneration`; from it on, the generation moves,
  the HLS manifest restarted from zero (`streaming.md` §6). PS1's wait before a lost feed becomes
  an incident is core's `PUBLISHER_GRACE_SECONDS`, not this.
- `failWorker` records three restarts at `doublingDelays(1_000, 4_000, 7_000)` (1, 2, 4 s), then
  reports one `workerFailed` with `final: true` at the last one's instant.
- `setFeedSample` feeds `sample()`, stamped at the instant it was set, with the publisher's
  protocol; jitter and lost packets are kept on WHIP alone.
- `markReady(ref, durationSec)` completes a recording.
- Capabilities: rtmps, srt, whip; whep, ll_hls; H.264 with AAC, and Opus on WHIP through the audio
  branch; playback over HLS, signed cookies and query token renewal both; recording and master at
  ingest; no DRM, no geographic restriction. A suite narrows them through the constructor.

**Signed playback.** `sign` signs ES256 with `PLAYBACK_SIGNING_KEY`, its `kid` in the header,
audience `arthome.cdn` (`adr-auth.md` §8.1), the claims given, a `prefix` claim, and `exp` from
`grant.expiresAt` (the token's 120 s are core's, D-020: the fake signs the expiry it is given). The
signature covers `/playback/{dateId}/{sessionScope}/`, the manifest and the segments, and never
sits in the URL: `manifestUrl` is the same across renewals; `query_token` answers the token beside
it, `signed_cookie` one cookie on the prefix. `edgeServes(path, credential, at)` is the edge's
decision for one request: a valid signature by a known `kid`, a path under the prefix (decoded
first, so an encoded `..` cannot climb out), and `at` before `exp`. A suite calls it to measure
playback stopping, not the renewal refused (`adr-stream-entitlement.md` §3.3).

**`MediaModule`** (`src/media/media.module.ts`) binds the fake under the four tokens through
`fakeOutsideProduction()`, which throws in production ("the fake streaming provider cannot be bound
in production"), and binds its own `CLOCK`, which a suite overrides.

**The keys** (`libs/config`). `readPlaybackSigningKey`: `PLAYBACK_SIGNING_KEY`, a P-256 private JWK
with its `kid`; outside production the published `play-development` key, distinct from the internal
token's (the playback and session sets are never the same, `adr-stream-entitlement.md` §3.4); in
production either development key is refused by its coordinates, under any `kid`.
`readStreamKeySecret`: `STREAM_KEY_SECRET`, 32 characters at least, the secret PS1 derives stream
keys from, with a development default refused in production.

**Never logged**: a presented stream key, a signed token, a cookie's value. The fake logs nothing;
anything a later PRD logs goes through `redactSensitive`.

## 0b. Run desk (PS1)

`src/run/`: a run per date, its stream key, its incidents, the eight run desk routes of
`streamingServiceApi` (`run-desk.controller.ts`, `incidents.controller.ts`), the ingest hooks and
two sweeper passes. The `Run` aggregate holds the row and its open incident (`data-model.md`
§5.1, §5.6); core's `assertRunTransition` decides every move.

- **Preparation.** `catalog.date.drafted.v1` (`prepare-run.handler.ts`, the one catalog type this
  module reads) inserts the run `idle`, its channel, a stream path of 128 random bits and
  `ingest_protocol` rtmps until a feed is accepted, `ON CONFLICT (date_id) DO NOTHING`: a second
  draft is `superseded`. A `date_id` or `channel_id` that is no UUID is dead-lettered at once.
- **The stream key is derived, never stored** (`stream-key.ts`): base64url HMAC-SHA-256 of
  `{runId}:{generation}` under `STREAM_KEY_SECRET`; `stream_key` keeps its SHA-256 digest per
  generation, one live per run. No list, event, log or console carries it. Reveal and rotation
  are the second phase.
- **Ingest** (`ingest-authorizer.ts`, `ingest-listener.ts`, attached at the API's boot by
  `IngestHooksAttachment`). The authorizer reads one statement and accepts only the path of a run
  not ended, with no publisher online, whose live digest equals the presented key's
  (`timingSafeEqual`); a refusal is logged with its reason and the run, never the key. The
  listener moves presence by conditional statements that refuse an instant older than the one
  recorded, and records the feed's protocol with its true monitor path (WHEP on a WHIP ingest
  that offers it, LL-HLS otherwise, D-019).
- **The version counts state, not presence.** Transitions, incidents and a first passed check
  save through `saveVersioned`; `publisher_online_since`, `publisher_lost_at`, the protocol and
  `after_grace_period` move by statements of their own (`updateReturning`), so a flapping feed
  never makes a studio command stale.
- **Routes.** Every command runs in one transaction: the idempotency record first
  (`runIdempotentlyVersioned` for the moves and the check, `runIdempotently` for incidents),
  the run under its lock, the save, the outbox rows (`record-run-events.ts`). The deadline is read
  before any work (`remainingBeforeDeadline`). A domain refusal is answered on its route by
  `refusedOn`, through `refuse`. `goOnAir` is also refused `publication.transition_forbidden`
  unless PS2's projected publication is `technical` (`none` when none is projected), and
  `state.conflict` while an incident is open: `on_air` always means no veil. No route reads a
  profile or a device, so none calls `profileOfPrincipal` or `assertSameCaller`: the principal's
  user is the actor, and a write without one, or on the `system` surface, is refused 403
  `api.forbidden` (`run-desk-call.ts`). Per-role authorisation is auth slice B's;
  `DenyInProductionGuard` stays. The check and the console read the metrics sample outside any
  transaction, within the caller's deadline (`sampleWithin`, 504 past it): a slow provider never
  holds the run's lock.
- **Incidents.** One open per run (`incident_open`, and the aggregate decides first); an insert is
  `ON CONFLICT DO NOTHING`, so a reused `incidentId` answers 409 `state.conflict`. One raised on air
  interrupts the run with its cause; elsewhere the state stays. Resolving returns an interrupted
  run to air; an incident already resolved answers its first resolution. Ending a run, by hand or
  by itself, resolves its open incident by the system first: `incident.resolved`, `run.ended`,
  then `run.state_changed`.
- **The passes** (`run-passes.ts`, both in the sweeper every second, `SweeperLoop`). Each reads its
  candidates without a lock through its partial index, then claims each run `FOR UPDATE SKIP
  LOCKED` in its own transaction and decides again on what it locked, so replicas share them.
  The presence pass: a publisher lost on air for `PUBLISHER_GRACE_SECONDS` sets
  `afterGracePeriod` ("publisher gone", `run.state_changed` with `after_grace_period` true, the
  version unmoved); lost for `HOLD_SCREEN_AUTO_AFTER_SECONDS_DEFAULT`, an automatic
  `hold_screen` incident, cause `venue_feed_lost`, interrupts the run. A publisher back clears
  "publisher gone" and, when core's `holdScreenLiftsOnFeedReturn` says so (D-124), resolves the
  automatic incident by the system in the same transaction, the run back on air. A final
  `workerFailed` raises an automatic `compatibility_worker_failed` incident, lifted by hand; with
  one open it is logged. The end pass (D-123): every live run with no publisher, page by page,
  ends at `runAutoEndsAt(endsAt(timing), publisher_lost_at, false)`, `ended_at` the last loss or
  the scheduled end, never before `started_at`, `ended_by` the system; a date with no timing never ends by itself, logged once
  per run and process.
- **Events** on `arthome.streaming.run`, key `date_id`: `run.technical_check_passed` (each pass,
  `passed_at` now), `run.started`, `run.ended` (no viewer peak: none is measured),
  `run.state_changed` (every transition, "publisher gone" and its clearing),
  `incident.raised`, `incident.resolved`. The actor is the principal's user on its surface, or
  `SURFACE_SYSTEM` with no account. `run-wire.ts` maps core's vocabularies to the proto's enums,
  an unknown member `UNSPECIFIED`.
- **`readRunFacts(manager, dateId)`** (`run-facts.ts`), for PS3, PS4 and PS5: one statement, no lock,
  `{ state, startedAt, endedAt, streamPath, incident }`, the open incident as the storefront reads
  it.
- **PS2's facts.** `date-facts.ts` binds PS2's `readDateFacts(manager, dateId)` behind
  `READ_DATE_FACTS`, which the suites override with the dates they project: the publication state
  for `goOnAir` (none projected reads `none`), the timing for the end by itself.

**Deployment order.** Migrate, then the consumer before the first draft in production, as
ticketing's §0: a draft read before the consumer exists is read from the topic's retention, so
nothing is lost within it. No backfill: the drafts within the retention prepare the runs of dates
already drafted.

- Two publishers on one key race the authorizer: both are accepted inside the authorise-to-online

## 0c. Entitlement projection (PS2)

`streaming`'s own copy of what decides a right to watch (`data-model.md` §4, the one projection that
carries authority): fed by ticketing's and catalog's events, read by PS3's verdict from local tables
with no call to another service (`adr-stream-entitlement.md` §5). No screen shows it.

**What each type writes.** Generated per type with `consumer-handler`, then grouped by table: nine
readers in `entitlement/entitlement-messages.ts` (spread into `consumed-messages.ts`'s `READERS`),
three commands, three handlers. Every other type on the three topics is `ignored`.

| Type | Topic, key | Writes |
| --- | --- | --- |
| `ticketing.seat.activated.v1` | `arthome.ticketing.date_sales`, `date_id` | `entitlement_seat`: an active seat, `ON CONFLICT (seat_id) DO NOTHING` |
| `ticketing.seat.cancelled.v1` | same | the seat cancelled, final, any reason (an unknown one too, D-095: a refund alone stops nothing) |
| `ticketing.subscription.changed.v1` | `arthome.ticketing.account`, `account_id` | `entitlement_subscription`: plan, state, openings, `paid_through`, guarded by `occurred_at` |
| `catalog.date.scheduled.v1` | `arthome.catalog.date`, `date_id` | `entitlement_date`'s timing, replay and rights groups, one transaction, applied when any group is |
| `catalog.date.rescheduled.v1` | same | the timing's `starts_at` |
| `catalog.date.replay_policy_set.v1` | same | the replay group |
| `catalog.date.rights_changed.v1` | same | the rights group |
| `catalog.publication.state_changed.v1` | same | the raw publication state (D-072), guarded by catalog's `version` |
| `catalog.date.outcome_declared.v1` | same | the outcome, guarded by `declared_at`: the latest declared wins (D-074, D-076) |

**The guards.** `claimMessage` in the transaction that writes the fact: the same `message-id`
answers `duplicate`. Each group is one `INSERT … ON CONFLICT (key) DO UPDATE … WHERE` its instant
is null or not older (`>=`), `RETURNING`: no row back is `superseded`. The publication's guard is
`excluded.version > kept.version`. Seats need no instant: an activation never overwrites, a
cancellation ends any active row, so every order of activation, cancellation, duplicate and a
retried older copy ends in one row. The schedule's `runtime_min` is taken whenever none is kept, so a
reschedule overtaking its schedule leaves `timing` null until both arrive, the newer start kept.
No lock across rows (§0's lock order).

**Ties.** Two facts of one group stamped with the same instant resolve by arrival (`>=`: the last
applied wins), so a retried older copy can re-apply over a newer one of the same millisecond. Open
with ticketing: a per-subscription version on `subscription.changed`, guarded like the publication
(`>`). The outcome is final once `cancelled` or `interrupted` (catalog's rule), whatever the
instants. A `seat.cancelled` needs only its `seat_id`: without an account, a date or an instant it
cancels the kept row by seat, and is dead-lettered only when no row exists.

**Fail closed on the unknown** (critical rule 10): an unknown plan opening is dropped; an unknown
publication state, rights scope or absent `rights` reads null, which PS3 refuses; an unknown replay
policy reads `none`; an unknown outcome is `ignored`, as ticketing's consumer does; an unknown
blackout reason reads null with its countries kept (upper-cased); an unknown subscription state opens
nothing. An id that is not a UUID, an empty `account_id` first, is dead-lettered at attempt 0
(permanent) for an activation: a seat with no account would open nothing, and is seen rather than dropped. Stored strings are mapped through core's member lists at read: a member this build does not know reads null (`none` for a replay policy) and an unknown opening is dropped.

**The read interface** (`entitlement/entitlement-facts.ts`), on the caller's manager, no lock:

- `readEntitlementFacts(manager, { accountId, dateId, now })`, one statement: `{ activeSeatsOnDate,
  seatExpired, planOpenings, date }`. `seatExpired` is C2's lost seat (a seat of the account on the
  date cancelled, none active); `planOpenings` is core's `planOpeningsOf` at `now` (D-125: active,
  trialing and past due open; cancelled until `paid_through`). PS3 passes the seat standing as
  unknown (`seatStanding: null`) and derives the ceiling with `concurrentStreamsAllowedFor`.
- `readDateFacts(manager, dateId)`, PS1's and PS5's: `DateFacts | null`, `{ dateId, channelId,
  timing, publicationState, outcome, rights }`; `timing` is core's `DateTiming`, its
  `roomOpensBeforeMin` from `DomainConstant.ROOM_OPENS_MINUTES_BEFORE`, null until `starts_at`,
  `runtime_min` and the replay policy are known; `channelId` null until a fact carrying it lands.

The ids are `uuid` columns: a caller passes a UUID it validated, or Postgres refuses the statement.
PS3 needs no callback: every renewal re-reads the facts, so a cancelled seat or a cancelled date
refuses the next one (`adr-stream-entitlement.md` §3.3).

**Freshness.** Every row keeps its fact's instant and `applied_at` from the injected clock. A fact
applied more than `ENTITLEMENT_PROJECTION_MAX_STALENESS_SECONDS` (5 s) after its instant logs
`read_model_staleness_seconds=<lag> type=<type> date=<id>` (or `account=`), the alert of
`context-map.md` §11. Measured on 2026-10-10 by `freshness.itest.ts` on the Kafka of
`@arthome-platform/testing`, consumer joined, 100 facts over the three topics produced one at a
time: visible after p50 13 ms, p95 29 ms, max 35 ms.

**Deployment order.** The consumer runs before the first seat is sold in production: the group reads
each topic from the start of its retention (168 h), with no backfill, so a seat older than the
retention is never projected and its holder is refused. The same holds for a date scheduled and for
a subscription last changed more than 168 h before the group first reads: with no row, the date reads
null and the account has no openings, the holders are refused (closed, but refused). A consumer
group whose offsets expire falls back to the same rule, so a stopped consumer is restarted inside the
retention. That first catch-up logs the staleness line
for every fact it replays, as it should.

## 0f. Replay asset (PS5)

`src/replay-asset/`: one `replay_asset` row per recorded date, the passes that move it and the
provider calls it owes. No route, no consumer: the run and the outcome reach it through PS1's and
PS2's tables. The provider stores and deletes, `streaming` decides (`adr-replay.md` §4).

- **States** (core's `REPLAY_ASSET_STATES`): `recording` (the start owed, then the run on air),
  `processing` (the run ended: stop owed, then the readiness polled), `ready` (announced, online
  until `expires_at`), `deleting` (the file to delete), `deleted` (final, `deleted_at`), `failed`
  (a call given up). The pure decisions are in `replay-asset.ts`; the SQL is in `replay-asset.store.ts`.
- **The passes** (`replay-asset-passes.ts`, each a `SweeperLoop` every second in
  `replay-asset-sweeper.module.ts`). Each reads its candidates without a lock through a partial
  index, then locks each asset `FOR UPDATE SKIP LOCKED` in a transaction of its own and decides
  again on what it locked, so replicas share them. None calls the provider.
  - *Request*: a run `on_air` or `interrupted` with no asset (`run_live`), when
    `readDateFacts` says the date has a replay mode (`hasReplayPolicy`) and no outcome that withdraws
    it, gets its asset `recording`, `recorded_from` the run's `started_at`,
    `ON CONFLICT (date_id) DO NOTHING`, one statement with no transaction around it: a date with
    no mode gets no row and so comes back every pass, at the cost of one read. One whose timing is
    not projected is looked at again on the next pass. An `interrupted` run keeps recording.
  - *Close*: a `recording` asset whose provider started it and whose run has an `ended_at` (D-115's
    automatic end included) becomes `processing`, `recorded_until` that instant.
  - *Withdraw*: an asset `recording`, `processing` or `ready` whose date's outcome is one core's
    `outcomeWithdrawsReplay` names (`cancelled`, `interrupted`) becomes `deleting`; `postponed`
    withdraws nothing. A `failed` asset is not taken back: it is an operator's.
  - *Expire*: a `ready` asset whose `expires_at` has come becomes `deleting`.
  - `replay.expired.v1` is written in the transaction that moves an announced asset (its
    `asset_ready` written) to `deleting`, expired or withdrawn; an asset never announced leaves none.
- **The calls** (`recording-calls.ts`, `RecordingCallSweeper`). The call due is read from the state
  (`callDue`): `recording` with no reference starts, on the run's `stream_path`; `processing` not
  stopped stops, then is polled with `status`; `deleting` is stopped first when it never was, then
  deleted (with no reference, nothing is called). A pass claims the assets due `FOR UPDATE SKIP
  LOCKED` in a short transaction that counts the attempt and moves `call_next_attempt_at` out by
  the backoff before the call; the call runs outside any transaction, bounded by
  `RECORDING_CALL_TIMEOUT_MS` (4 s, below the shortest lease, so no replica claims it again while in
  flight), and its outcome is written in one of its own, locking the row `FOR UPDATE` and deciding
  again on it. The backoff doubles from 5 s to 5 min with up to a fifth of jitter, for about an
  hour: `RECORDING_ATTEMPTS_MAX` attempts, then the asset is `failed`, `failed_call` the call's
  name, `call_dead_at` set, one error log with the date. Each failed attempt (a timeout included)
  logs a warning with the date, the call, the attempt and the error's name. A recording the
  provider no longer knows (`RecordingNotFound` on `status`) is given up at once. Only a failed
  provider call counts toward the give-up: when the outcome cannot be written, the call is asked
  again at the end of its lease, never `failed` for it.
- **A recording started that the asset does not keep** (its outcome not written, another start won
  meanwhile, or a start answering after its timeout) is deleted at the provider once the
  transaction has committed, never inside it, up to `ORPHAN_DELETE_ATTEMPTS` (3) times; an error
  log names the date. If all three fail, the error log says it is left at the provider: the
  reference is in no row then, and only the provider's listing finds it.
  A poll that answers not ready is not a failed call: the attempts restart and the next poll is
  `READINESS_POLL_EVERY_MS` (30 s) away, until `READINESS_GIVE_UP_AFTER_MS` (6 h) after the run's
  end. The `RecordingRef` stays in its column: no event, log or answer carries it.
- **Readiness.** A poll answering ready with a duration commits in one transaction: `asset_ready.v1`
  on the outbox through `writeStreamingEvent` on the transaction's manager, then `ready`,
  `duration_sec`, `available_from` (the instant observed) and `expires_at` =
  `replayClosesAt(run.ended_at, replay_window_hours)`, the run's real end: an overrun cannot give two
  closings. If the date's outcome withdraws the replay by then, or its window has already closed
  (a readiness later than the window), the asset goes to `deleting` with no event.
- **Events** on `arthome.streaming.run`, key `date_id`, through `replay-asset-wire.ts`:
  `streaming.replay.asset_ready.v1` and `streaming.replay.expired.v1`.
- **The query an operator runs for `failed` assets:**

  ```sql
  SELECT date_id, failed_call, call_attempts, call_dead_at, recorded_until
    FROM replay_asset WHERE state = 'failed' ORDER BY call_dead_at;
  ```

  No alert is wired yet: the give-up's error log is the only signal. To retry one, once the
  provider is back: `UPDATE replay_asset SET state = 'deleting',
  call_attempts = 0, call_next_attempt_at = NULL, call_dead_at = NULL, failed_call = NULL WHERE
  date_id = $1` for a file to remove; a `ready` replay is never rebuilt by hand.
- **Until the replay slice** the closing is computed here with `replayClosesAt` from the run's end
  and the projected window, and the withdrawal is read from the outcome. When catalog's `Replay`
  publishes `catalog.replay.state_changed.v1` with its closing and its withdrawal, the replay slice
  switches the source of `expires_at` and of the withdraw pass to it; `replayClosesAt` on the same
  inputs gives the same instant.
- **A run that ends before the request pass has seen it** (the pass runs each second, a run on air
  lasts hours) is not recorded: the request pass reads live runs only. Not a case the fake can
  produce; a real provider's adapter must record from the ingest regardless.
- **The sweeper does not boot in production** while the fake is the only provider, as the API
  (`MediaModule`, §0a).

**Deployment order.** Migrate, then the sweeper. No backfill: a run already on air with a mode is
requested by the first pass.
